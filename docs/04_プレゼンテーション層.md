## 1. 目的とスコープ

設計書01〜03で確定した状態・データを、実際に画面へ描く層を定義する。対象は4つ：

1. **Glance Widget**（世界観の主舞台）
2. **Live Updates通知**（チップ＋シェード、フォールバック含む）
3. **アプリ本体UI**（編成／回収・開封／コレクション／指名覚醒・魔力に還す）
4. 横断事項：UiStateマッピング原則、ナビゲーション、素材規約、検証方法

---

## 2. モジュール構成と共通原則

```
:app                     — シェル。ナビゲーション、DI組み立て
:widget                  — Glance実装（受信機・描画・配置ロジック）
:notification            — Live Updates／フォールバック通知のビルダー
:feature:expedition      — 編成→点火、回収→ログ→開封
:feature:collection      — 住人一覧、指名覚醒、魔力に還す、ニックネーム
:core:ui                 — 共通UiStateマッパー、テーマ、開封カード等の共有部品
```

### 原則G：サーフェスは「UiStateの純関数レンダラ」である

各サーフェスは `(SessionRow?, 付随クエリ, now) → UiState → 描画` の一方向とし、**UiStateマッパーは `:core:ui` の純Kotlin関数**に集約する。Widget・通知・アプリで `derive()` の解釈がずれる余地をなくし、マッパー単体をJVMテストで検証する（01原則Bのプレゼンテーション版）。

```kotlin
// :core:ui — 三層すべてがこれを通る
fun mapWidgetState(s: ExplorationSession?, residents: List<Resident>, now: Instant): WidgetUiState
fun mapNotificationState(s: ExplorationSession?, leader: Resident?, now: Instant): NotifUiState?
```

## 3. Glance Widget

### 3.1 サイズクラスと表示容量

アート仕様のS/M/Lサイズクラスと、Widgetのグリッドサイズを対応させる。

| Widgetサイズ | グリッド目安 | 背景 | 住人表示上限（叩き台） |
|---|---|---|---|
| Small | 2×2 | ベース（アート発注仕様#11）＋空・光レイヤー | 2体（M級1＋S級1 目安） |
| Medium | 4×2 | ベース1枚 | 4体（L級は1体で2枠換算） |
| Large | 4×3以上 | ベース＋装飾 | 7体（L級2枠換算） |

表示上限を超える留守番組は**日替わりローテーション**で入れ替える（次項の導出関数に吸収。「今日は誰が前庭にいるか」自体を眺める楽しみにする）。

### 3.2 表示導出関数（01 §6.2の実装定義）

```kotlin
// 純Kotlin。追加の永続状態ゼロ
fun deriveWidgetScene(
    session: ExplorationSession?, caretakers: List<Resident>,
    snapshotOrToday: ContextSnapshot, now: ZonedDateTime, sizeClass: WidgetSize,
): WidgetScene {
    val slot = now.toInstant().epochHour()         // 配置更新の粒度: 1時間（DEC-12）
    val rng = Rng(subSeed(slot.toLong(), "widget.scene"))
    // 1) 表示メンバー選抜（上限まで。隊長不在=EXPLORINGの空きはそのまま残す）
    // 2) 各メンバーの立ち位置を決定論的に抽選（住人スプライトは待機1姿勢）
    // 3) 背景バリアント: 天気(snapshot or 当日値) × 時間帯(now)
}
```

- 粒度 `epochHour` により「1時間ごとに住人の立ち位置が変わる」。同じ時間枠なら全端末・全Widgetで同じ絵になり、30分枠は使わない（DEC-12）
- 天気について：EXPLORING中は**セッションのスナップショット値**（探索の物語と修正値の根拠を一致させる）、IDLE中は `effectiveWeather(now)`（03 §2.1）。この使い分けを明記する
- 天気が `UNKNOWN`（未設定・未取得・6時間より古い）のときは**晴れの空レイヤー**で描く（見た目だけの既定値。ゲーム判定は中立のまま）
- 時間帯は `timeBandOf(now.toLocalTime())`（02 §2と共有。05:00–16:59 昼／17:00–18:59 夕／19:00–04:59 夜）。`now` は端末のタイムゾーンを含む `ZonedDateTime` で受け、現地時刻で判定する。空は常に「今」の時間帯で描き、スナップショットの `timeBand` は修正値判定にだけ使う

### 3.3 Glance実装上の制約と対応

- **静止画差し替えのみ**。住人ごとのスプライトは待機1姿勢とし、更新時に変えるのは配置と背景だけ
- 住人・背景は**個別ドローアブルの重ね合わせではなく、可能な限り事前合成**を検討（RemoteViewsのビュー数・Bitmapメモリ上限対策）。ただし配置バリエーションと相性が悪いため、PoCでは「背景1枚＋住人スプライトN枚の重ね」で始め、実機でメモリ・描画確認後に判断（要確定）
- 更新契機は01のRefresh系統に完全一致：`onUpdate`／帰還アラーム／トラッカー更新Worker／アプリからの明示更新。**Widget独自のタイマーは持たない**

### 3.4 タップ領域

| 領域 | IDLE | EXPLORING | RETURNED |
|---|---|---|---|
| Widget全体 | アプリ（編成画面） | アプリ（探索状況＝ログ途中経過は見せず、残り時間のみ） | **回収画面へディープリンク** |

PoCではタップ領域は全体1枚で開始（住人個別タップは製品版の検討事項）。

## 4. Live Updates通知（`:notification`）

### 4.1 ビルダー仕様（Android 16+）

| 要素 | 値 | 根拠・参照 |
|---|---|---|
| スタイル | `ProgressStyle`、start＝遺跡入口アイコン／end＝ホームアイコン | 01 §6.3 |
| トラッカー | 隊長のカラーアイコン（`setProgressTrackerIcon`、更新可） | 01 §6.3 |
| チップ | smallIcon（モノクロ**ランタン**シルエット）＋ `setWhen(endAt)` カウントダウン | 01 §6.3 |
| トラッカーのフォールバック | 編成が空のときはランタンアイコン（固定の主人公は存在しない） | 01 §6 |
| フラグ | ongoing、`contentTitle` 必須、RemoteViews不使用、`POST_PROMOTED_NOTIFICATIONS` 宣言 | promoted要件 |
| RETURNED時 | ProgressStyle終端＋「精霊が帰ってきた」、タップ→回収ディープリンク | 01 §6.1 |

### 4.2 トラッカー位置の更新（要確定だった間隔の設計案）

- 本番定数（探索2時間〜）：**WorkManager周期15分**で再投稿。8〜32回/周で位置更新として十分。01 §10の「保険的定期Refresh」とこのWorkerを**1本に統合**する（再投稿＝Refreshそのもの）
- デモ定数（探索3分）：WorkManagerの15分下限に掛かるため、**セッションをN分割（例：6分割＝30秒毎）した `setExact` アラーム列**で代替。少数回・短時間なので許容。定数セット切替（02 §6）にアラーム戦略も含める
- 位置計算は `progress = (now − startedAt) / (endAt − startedAt)` の導出値。Workerが遅れても次回起動時に正しい位置へ飛ぶ（原則B/C）

### 4.3 フォールバック階梯（Android 16未満）

| 環境 | 表現 |
|---|---|
| A16+（promoted承認） | チップ＋ProgressStyle＋トラッカー（フル） |
| A16+（promoted否認＝審査未確定リスク） | 通常常駐通知＋ProgressStyle（シェードのみ。トラッカーは残る） |
| A14〜15 | 通常常駐通知＋標準プログレスバー＋ `setUsesChronometerCountDown` |
| 通知権限拒否 | 通知層なし。**Widgetと帰還アラームだけでコアループは完全に成立**することを仕様として保証（通知は増幅装置であり前提ではない） |

### 4.4 通知チャネルと権限文脈

`POST_NOTIFICATIONS` は初回Ignite直前に「精霊の帰りを知らせるため」の文脈付きダイアログ（コアループ仕様書§9踏襲）。チャネルは「探索の見守り」「帰還のお知らせ」の2本（前者を下げても後者だけ残せる構成）。

## 5. アプリ本体UI（`:feature:*`）

### 5.1 画面一覧とナビゲーション

```
home（遺跡ビュー簡易版・状態別CTA）
 ├─ party（編成：3枠、[0]=隊長。前回編成プリセット済み→「灯す」1タップ）
 ├─ collect（回収：ログ再生→開封→リザルトサマリ）
 ├─ collection（住人一覧：フィルタ/ソート、locked切替、ニックネーム編集、複数選択→魔力に還す）
 └─ shrine（天井：魔力ゲージ＋図鑑グリッドから指名覚醒）
```

ディープリンク：`app://collect`（Widget/通知のRETURNEDタップ）、`app://home`（それ以外）。**Collectハンドラの原則Dガードはディープリンク着地時に評価**し、不成立なら黙ってhomeへ（01 §5）。

### 5.2 回収・開封フロー（コアループの山場）

1. **ログ再生**：構造化 `LogEvent` 列（02）をタイプライタ風に流す。タップで全文即時表示（スキップ）。文言は平易で短く、過度に古風な表現を避ける。テンプレートはUI層リソースに置き、多言語・文体調整をエンジンから分離する（DEC-09）
2. **開封**：**1体ずつカードをめくる**（コアループ仕様書§11の有力案を採用）。カードは ★（最重要・最大表示）→ 性格ラベル → 色（レア色以上はカード背景・発光エフェクトで先に「格」を予告）の順で開示
3. **サマリ**：獲得住人一覧＋魔力加算＋天井ゲージの伸び。ここから「もう一度灯す」導線（再出発の最短化）
4. 複数体時は「残りをまとめて開ける」ボタンを2体目以降に表示（デモ映えと日常の手間の両立、同§11のトレードオフへの解）

### 5.3 編成（party）

- 3枠固定（03 §7の叩き台採用）。枠タップ→コレクションから選択。**枠[0]に隊長バッジ＋「通知に表示されます」注記**（隊長概念のチュートリアルを兼ねる）
- ヘッダ：「千葉・☔雨 ／ 木曜・植物の祭壇」の形式で、地域名・今日の天気・曜日・曜日祭壇の材質を表示。タップで地域選択ダイアログ（05 §6.6）。地域未設定時は「地域を選ぶ ›」
- 修正値プレビュー（v0.3確定）：編成中の各住人について `arrowsFor(slot, party, snapshot予定値)`（02 §5.3）の結果を**矢印の本数**で表示する。数値（％）は出さない（定数調整で文言が変わらないように）
  - 表示例（雨・木曜の日）：`壺 ↑ 雨`／`燭台 ↓ 雨`／`供物の果実 ↑↑ 木曜の祭壇・隊長の先導`。内訳は `Arrows.sources` のラベルをそのまま使う
  - 鎮めの矢印と魔力の矢印は行を分ける（魔力は「💠↑」のように記号を変える）
  - **UI側で判定を再実装しない**。プレビューはエンジンと同じ関数の出力であり、点火時にそのままスナップショットされる（02 §8のプレビュー一致テスト）

### 5.4 コレクション・魔力に還す・指名覚醒・ニックネーム

- 一覧カード＝開封カードの縮小版（★/性格/色が一目)。ソート：新着/★/モチーフ
- 魔力に還す：複数選択モード→合計魔力プレビュー→確認ダイアログ（文言は世界観語「魔力に還す」）。`locked`・編成中は選択不可（03 §4.4）
- ニックネーム：一覧カードのタップ→名前入力ダイアログ。開封サマリ（§5.2-3）にも「名前をつける」導線（任意・スキップ可）。表示は nickname ?: モチーフ名
- shrine：魔力ゲージ（`lifetimeEarned` 演出＋ `balance` 実残高）＋発見済みモチーフのグリッド。未発見はシルエット。選択→コスト確認→`namedAwaken`→開封カード再利用

## 7. 検証方法（AI Agent自走ループ）

- **UiStateマッパー**：JVMユニットテスト（フェーズ×データ組合せの表駆動）。三層の表示矛盾はここで潰す
- **Glance**：`glance-appwidget-testing` でツリー検証＋ `adb` スクリーンショットの目視/差分（PoC方針のbuild→install→screenshot自走ループ）
- **通知**：ビルダー出力のフィールド検証（JVM）＋実機でのpromoted昇格可否の手動確認（§8）
- **デモ定数モード**：3分セッションで「灯す→チップ→帰還→開封」の全経路をエミュレータ1本で通す E2E スクリプトを `adb` ベースで用意
