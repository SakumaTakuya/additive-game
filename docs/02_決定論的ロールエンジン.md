## 1. 目的とスコープ

「シード値から探索1周の結果（バトルログ・覚醒個体・魔力）を一括計算する決定論的処理」（コアループ仕様書§9で確定）を、実装可能なモジュールとして定義する。本書が定義するのは：

1. **決定論の境界**：エンジンへの入力の完全な列挙と、外部依存のスナップショット原則
2. **PRNGの選定とストリーム分割**：バージョン間・チューニング間で結果が壊れない乱数設計
3. **計算パイプライン**：遭遇→鎮め→覚醒→個体ロールの固定順序と各段の定義
4. **数値検証**：PoC初期定数での厳選期待値（モンテカルロ実施済み、§7）
5. **テスト戦略**：`gradlew test` で完結する自己検証（AI Agent開発方針との接続）
6. **修正値モデル**（v0.4）：性格・材質・曜日祭壇が鎮めと魔力にどう効くか（§5.3）

魔力天井の消化（指名覚醒）や重複→魔力変換はコレクション側（設計書03）の責務とし、本エンジンは「1周分の結果生成」のみを担う。

## 2. 決定論の境界：エンジンは純関数である

```
ExpeditionResult = RollEngine.resolve(seed, snapshot, party, constants)
```

同じ4引数からは**バイト単位で同一**の結果が出る。

`party` は編成の各住人の**不変な属性**（`motifId`・`star`・`personalityId`）を `[0]`＝隊長の順で並べた値である（v0.5追加）。住人の★・性格・モチーフは覚醒後に変わらず、編成中の個体は「魔力に還す」の対象外（設計書03 §4.4）なので、回収時に `session.partyIds` から読み直しても点火時と同じ値になる。ニックネーム・保護フラグは計算に使わない。

決定論を成立させるための原則：

- **原則E：外部世界はIgnite時にスナップショットする**
  天気（API取得値）・日付（曜日・曜日祭壇・月齢の導出元）・点火時刻の時間帯などの修正値ソースは、探索中に変わりうる外部データである。これらを回収時に参照すると決定論が壊れる（回収を遅らせると結果が変わる＝再現不能・テスト不能）。よって**点火時に `ContextSnapshot` として固定し、セッションレコードに保存する**。六曜はPoCでは使わない（旧暦変換が必要で誤りやすく、テストの正解値も用意しにくいため）。
- **原則F：エンジンは時刻・I/O・プラットフォームAPIに一切触れない**
  `System.currentTimeMillis` も `kotlin.random.Random.Default` も禁止。入力は引数の4つだけ。これにより純KotlinのユニットテストがエミュレータなしでCI完結する。

### 設計書01への波及（v0.3で反映済み／v0.4追加分は01 v0.5で反映）

`ExplorationSession` に `snapshot: ContextSnapshot` フィールドを追加した（設計書01 §3参照。保存先はRoomの `session` 行）：

```kotlin
data class ContextSnapshot(
    val date: LocalDate,        // 曜日・曜日祭壇・月齢の導出元（端末タイムゾーンのローカル日付）
    val timeBand: TimeBand,     // v0.4追加：点火時刻の時間帯
    val weather: WeatherKind,   // 点火時点の保存値（固定地域の「今日の天気」）。v0.4で UNKNOWN を追加
)

enum class WeatherKind { SUNNY, CLOUDY, RAIN, SNOW, UNKNOWN }  // 見た目（空レイヤー）用の4種＋中立
enum class WeatherGroup { SUN, CLOUD, WET, NONE }              // ゲーム判定用：雨・雪＝WET、UNKNOWN＝NONE（中立）
enum class TimeBand { DAY, EVENING, NIGHT }                    // 05:00–16:59 ／ 17:00–18:59 ／ 19:00–04:59
```

- 状態機械の遷移・不変条件には影響しない（不変の事実が増えるだけ。TLA+再検証不要）。v0.4の `timeBand` 追加も同様
- `timeBandOf(LocalTime)` と `WeatherKind.group` は `:core:model` に置き、Widgetの空レイヤー（04 §3.2）と**同じ関数を共有**する
- 天気の取得・保存・有効期限はエンジンの外で解決する（設計書03 §2.1、01 §4）。エンジンは渡された `weather` を読むだけで、`UNKNOWN` のときは天気条件の修正値がすべて不発になる（中立）

## 3. PRNG：SplitMix64を自前実装で固定する

**`kotlin.random.Random(seed)` は使わない。** Kotlin標準の乱数アルゴリズムは言語バージョン間での安定性が保証されておらず、Kotlinを上げただけでゴールデンテストと過去セッションの再現性が壊れる。`java.util.Random` は仕様固定だが品質が低くマルチプラットフォーム展開も阻む。

採用は **SplitMix64**（約10行、公有アルゴリズム、品質十分、リポジトリにコミットして固定）。

### ストリーム分割（サブシステム独立の原則）

1本の乱数列を全工程で順番に消費すると、「遭遇数の定数を1つ変えただけで、以降の全ロール結果がずれる」というチューニング地獄が起きる。よって**サブシステムごとに独立ストリームを導出する**：

```kotlin
fun subSeed(seed: Long, label: String): Long =
    splitMix64(seed xor fnv1a64(label))

val encounterRng = Rng(subSeed(seed, "encounter"))
val quellRng     = Rng(subSeed(seed, "quell"))
val awakenRng    = Rng(subSeed(seed, "awaken.count"))
// 個体ロールは個体インデックスまで含めて分離
val starRng_i    = Rng(subSeed(seed, "awaken.$i.star"))
val persRng_i    = Rng(subSeed(seed, "awaken.$i.personality"))
val colorRng_i   = Rng(subSeed(seed, "awaken.$i.color"))
val motifRng_i   = Rng(subSeed(seed, "awaken.$i.motif"))   // v0.5追加：④のモチーフ抽選（ADR D-014）
```

- **効果1**：遭遇テーブルを調整しても覚醒個体のロールは不変（差分テストが意味を持つ）
- **効果2**：個体単位でも軸単位でも独立なので、「★だけ再計算」等のデバッグが容易
- **効果3**：ストリーム独立性そのものをテストできる（§8）

## 4. 計算パイプライン（固定順序）

`resolve()` 内部は以下の5段。**順序と各段の入出力を凍結**し、変更時は設計書改訂を必須とする。

| 段 | 入力 | 出力 | 備考 |
|---|---|---|---|
| ① 遭遇生成 | `constants.expeditionMinutes`, 深度, encounterRng | 遭遇列 `List<Encounter>`（相手モチーフ＝初期住人テーブルの寝ぼけ個体、時刻オフセット） | 敵専用テーブルなし（住人リスト転用） |
| ② 鎮め解決 | 遭遇列, party, snapshot, quellRng | 各遭遇の成否、鎮め成功数 `q`、敗北なら早期帰還フラグ | **PoCは MinimalBattleResolver**（§5.1〜5.2）。修正値は §5.3 の矢印モデル（天気・時間帯・曜日・月齢 × 材質・性格）。案1採用のため早期帰還も表示・減額のみで endAt 不変 |
| ③ 覚醒数決定 | q, awakenRng | 覚醒数 `n ≥ 1` | 1体確定＋戦果上振れ。下限1はコード上の不変条件として `check()` |
| ④ 個体ロール | n, q, snapshot, 各個体Rng | `List<ResidentRoll>`（モチーフ・★・性格・色） | ★分布は鎮め補正でシフト（§5.4）。性格・色は補正なし独立 |
| ⑤ ログ・集計 | ①〜④の全結果, party, snapshot | `ExpeditionResult`（構造化ログ、覚醒個体列、魔力量） | 魔力量は魔力の矢印で増減（§5.3）。ログは**構造化イベント列**であり文字列ではない（文言・多言語はUI層の責務） |

### 出力型

```kotlin
data class ExpeditionResult(
    val log: List<LogEvent>,          // sealed: Encountered / Quelled / Failed / Found / Awakened
    val awakened: List<ResidentRoll>, // n ≥ 1 を型では表せないため check() で保証
    val manaGained: Int,
    val earlyReturn: Boolean,         // 表示・減額用（endAtは不変：設計書01 §9 案1）
)

// v0.5で凍結（2026-08-26決定 D-002 の再反映）。型・フィールドの追加/変更は本設計書の改訂を必須とする。
// 1遭遇 = Encountered → (Quelled | Failed) → Found（Quelled時のみ）の最大3イベント。全遭遇の後に Awakened を n 個。
// 早期帰還はイベント型を追加せず ExpeditionResult.earlyReturn で表現する（UI層が定型文を差し込む）。
// index は遭遇列の添字。ゴールデンテスト差分で「何番目の遭遇が変わったか」を読めるようにするため。
// 文言・多言語はUI層テンプレートの責務（エンジンは文字列を持たない）。
sealed interface LogEvent {
    data class Encountered(val index: Int, val motifId: Int, val atOffsetMin: Int) : LogEvent
    data class Quelled(val index: Int) : LogEvent
    data class Failed(val index: Int) : LogEvent
    data class Found(val index: Int, val mana: Int) : LogEvent   // 遭遇1件分の魔力（表示用の内訳）。manaBase はログに出ないため Σmana と manaGained の一致は要求しない
    data class Awakened(val rollIndex: Int) : LogEvent           // awakened リストの添字
}

data class ResidentRoll(
    val motifId: Int,                 // 初期住人テーブル参照
    val star: Int,                    // 1..5
    val personalityId: Int,           // 0 until constants.personalityCount
    val color: ColorTier,             // NORMAL / RARE / GLOW
)
```

### 指名覚醒API（v0.2追加・設計書03 §4.3から呼ばれる）

魔力天井の出口＝指名覚醒（確定）に対応する第2のエントリポイント：

```kotlin
fun resolveNamed(seed: Long, motifId: Int, constants: RollConstants): ResidentRoll
```

- モチーフは引数で確定。**★・性格・色は通常ロール**（★は鎮め補正なしの `base` 分布。天井の価値は「狙いモチーフの試行を魔力で買える」ことに限定し経済をシンプルに保つ — 設計書03 §7の推奨を採用）
- ストリームラベルは `"named.star"` / `"named.personality"` / `"named.color"` とし、通常覚醒（`"awaken.$i.*"`）と完全分離。定数調整の相互不干渉を維持する
- シードは呼び出し側（設計書03）が実行時採番。テストではシード注入で決定論検証する
- ゴールデンテスト・統計テスト（§8）の対象に `resolveNamed` も含める

## 5. 鎮め解決：バトルの差し込み点・勝率式・修正値モデル

### 5.1 BattleResolver インターフェース

バトルの実装範囲を、**差し替え可能な1インターフェースに閉じ込めて先送りコストをゼロにする**：

```kotlin
interface BattleResolver {
    fun resolve(encounters: List<Encounter>, party: Party,
                snapshot: ContextSnapshot, rng: Rng): BattleOutcome
}
// PoC採用 : MinimalBattleResolver — 成否判定のみ（勝率＝§5.2の1式）。v0.4で確定
// テスト用: NoBattleResolver      — 全遭遇スキップ、q=0（素の★分布）。デバッグ・比較用に残す
// 製品版  : FullBattleResolver    — 材質同士の相性・敵傾向の事前提示込み
```

コアループ・状態機械・回収UIはどれを選んでも不変。

**v0.4でPoCは MinimalBattleResolver に確定した。** 性格12種のうち10種が鎮めに効く（§5.3）ため、NoBattleResolver では「性格一致」を狙う厳選が意味を失う。

**材質同士の相性（編成の材質×寝ぼけ個体の材質）はPoCに入れない。** 遭遇は点火後にシードから決まり、編成時には見えない。対策できない相性は攻略にならず、結果のぶれにしかならない。敵の傾向を事前に見せる仕組みとセットで製品版で扱う。PoCの相性は、点火前に編成画面で見える**天気・時間帯・曜日・月齢**との相性に限定する（§5.3）。

### 5.2 PoCの勝率式（MinimalBattleResolver）

各遭遇の鎮め成否は、編成全体で共通の勝率 `p` で判定する。

```
p = min(P_MAX, max(0, Σ_i ( MEMBER_BASE + STAR_PT × (★_i − 1) + ARROW_PT × quellArrows_i )))
各遭遇：quellRng.nextDouble() < p なら鎮め成功（q に加算）
```

- 和は編成中の住人（最大3体）について取る。**空編成は p = 0**（鎮める者がいない → q = 0 → 素の★分布）。人数が多いほど鎮めやすい
- `quellArrows_i` は住人 i の鎮めの矢印の正味本数（↑＝+1、↓＝−1。§5.3）。**この値がそのまま編成画面の修正値プレビューと住人詳細の「今日の相性」に出る**
- 1体以上いれば p は正になる（最悪ケース：★1・欲張り・雨の日の火でも 0.02）
- 深度による減算はPoCでは持たない（深度固定。ランタン強化＝深度の成長軸は未確定事項）

| 定数 | 叩き台 | 意味 |
|---|---|---|
| `MEMBER_BASE` | 0.12 | 1体あたりの基礎寄与 |
| `STAR_PT` | 0.02 | ★1つあたり（★1→+0、★5→+0.08） |
| `ARROW_PT` | 0.05 | 鎮めの矢印1本あたり |
| `P_MAX` | 0.90 | 勝率上限（必ず鎮められる状態を作らない） |
| `encounterRatePerHour` | 3.0 | 探索2時間で平均6遭遇（ポアソン） |

モンテカルロ（20万周、探索2時間＝平均6遭遇、`QUELL_NORM`=5、§5.4の補間）：

| 編成の状態 | p | 鎮め数 E[q] | ★5率 | ★4+率 | 3軸同時の期待覚醒数（性格12種） |
|---|---|---|---|---|---|
| 空編成 | 0.00 | 0.00 | 3.0% | 15.0% | 889体 |
| 1体・★3・相性なし | 0.16 | 0.96 | 4.3% | 17.9% | 746体 |
| 3体・★2〜3・相性なし | 0.46 | 2.76 | 6.7% | 23.0% | 580体 |
| 3体・★2〜3・矢印+3本 | 0.61 | 3.65 | 7.7% | 25.1% | 532体 |
| 厳選済み・相性の強い日（上限） | 0.90 | 5.39 | 9.0% | 27.8% | 479体 |

- 厳選（★）と相性（矢印）の効き方が**単調**で、空編成は素の分布に**自然に退化**することを確認
- 差は★5率で 3%→9% の幅に収まる。「編成を考えると得、考えなくても損はしない」という放置ゲーの幅になっている
- 探索を長くする成長軸（6〜8時間）を入れると遭遇数が増えて q が `QUELL_NORM` で頭打ちになり、**性格・材質の差が消える**。成長軸を入れる場合は §5.4 の `t` を遭遇数比（`q / 遭遇数`）ベースに変える（§9）

### 5.3 修正値モデル（矢印）

#### 判定の3原則

1. **効果の行き先は2つだけ**：**鎮めの矢印**（§5.2の勝率へ）と**魔力の矢印**（⑤の魔力量へ）。★・色・覚醒数・終了時刻・遭遇生成には直接触れない。★と覚醒数は鎮め成功数 q を経由して間接的に動く（§4のパイプラインは不変）
2. **条件は点火時点のスナップショットで判定し、探索中は変えない**（原則E）。途中で雨が止んでも夜が明けても判定は点火時のまま。したがって**編成画面のプレビュー＝実際の計算入力**
3. **強さは条件の起きやすさで決める**：常時 → ↑、よく起きる（天気・時間帯）→ ↑↑、たまにしか起きない（週末・満月・祭壇一致）→ ↑↑↑。**材質は性格より1段弱い ↑ にそろえる**（材質はモチーフで決まり誰でも選べる。厳選の報酬である性格のほうを大きくする）。厳密な期待値の均衡は取らない。天気・曜日は現実由来で地域や生活時間に依存するため、**自分の遊ぶ時間帯・曜日に合う性格がその人にとっての当たり**になる

#### 性格12種（`Personality` enum、`:core:model`）

`personalityCount = 12` で確定。**並び順が永続化されるID**（`resident.personalityId`）であるため、追加は末尾のみ、削除・並べ替えは禁止。

| ID | 性格 | 略 | 条件（点火時に判定） | 鎮め | 魔力 | 説明文（住人詳細・叩き台） |
|---|---|---|---|---|---|---|
| 0 | 穏やか | 穏 | 常時 | ↑ | | いつでも落ち着いて鎮められる |
| 1 | 晴れ好き | 晴 | 天気が SUN | ↑↑ | | 晴れの日、鎮めがうまくいきやすい |
| 2 | 曇り好き | 曇 | 天気が CLOUD | ↑↑ | | 曇りの日、鎮めがうまくいきやすい |
| 3 | 雨好き | 雨 | 天気が WET（雨・雪） | ↑↑ | | 雨や雪の日、鎮めがうまくいきやすい |
| 4 | 昼行性 | 昼 | 時間帯が DAY | ↑↑ | | 昼に灯すと、鎮めがうまくいきやすい |
| 5 | 夜行性 | 夜 | 時間帯が NIGHT | ↑↑ | | 夜に灯すと、鎮めがうまくいきやすい |
| 6 | のんびり屋 | 休 | 土曜・日曜 | ↑↑↑ | | 週末は、とても調子がいい |
| 7 | 月夜好き | 月 | 月齢 13.0〜17.0 日（満月前後） | ↑↑↑ | | 満月のころ、とても調子がいい |

| 9 | 先導役 | 導 | 自分が隊長枠（party[0]） | 編成全員に ↑ | | 隊長にすると、仲間みんなが鎮めやすくなる |

- 略字は編成枠・一覧カードの「材質・性格」表示用（05 §6.2の「石・穏」形式）。12種で重複なし
- 天気が NONE（中立）の日は、天気条件の性格（1〜3）はすべて不発。時間帯 EVENING（夕）はどの性格も発動しない中立帯

#### 材質7種（`Material` enum）と天気・曜日祭壇

v0.4で**植物**を追加し7種とした（#10 供物の果実の材質が「土（植物）」で、6種のどれにも収まっていなかったため）。

| 材質 | モチーフ | 得意な天気（鎮め ↑） | 苦手な天気（鎮め ↓） | 祭壇の曜日（鎮め ↑） |
|---|---|---|---|---|
| 水 | #01 スライムの精霊・#02 しずく | WET | | 水曜 |
| 土器 | #03 壺 | WET | | 土曜 |
| 石 | #05 結晶・#07 門番の石像・#08 壁画の獣 | CLOUD | | 日曜 |
| 骨 | #04 ドラゴンの化石 | CLOUD | | 月曜 |
| 金属 | #09 鍵束 | SUN | | 金曜 |
| 火 | #06 燭台 | SUN | WET | 火曜 |
| 植物 | #10 供物の果実 | SUN | | 木曜 |

- 天気ごとに得をするモチーフ数は SUN 3・CLOUD 4・WET 3。どの天気でも編成が組める
- **苦手（↓）は「雨の日の火」の1つだけ**。誰にでも直感的に分かる組み合わせに限る
- **曜日祭壇**：その日に祀られる材質の住人の鎮めが ↑。火・水・木・金・土は曜日の字のまま（木＝植物、金＝金属、土＝土器）、月曜は骨（月明かりに白く浮かぶ）、日曜は石（日を浴びて温まる）。日付から導出するため、永続状態・スナップショットの追加は不要

- v0.3の仮ルール「雨→石・土器が有利」は本表で置き換える（石は曇りへ移動）
- 世界観上の説明：雨は水と土器が吸って満ち、曇りは日差しを嫌う骨と石が落ち着き、晴れは火・植物・金属が陽を受けて元気になる

#### 月齢の計算（近似式で十分）

`moonAge` と曜日祭壇の材質 `shrineMaterialOf(date)` は `:core:model` に置く（v0.5）。編成画面ヘッダ（設計書04 §5.3）とエンジンが同じ関数を使う。

```kotlin
// 天文精度は不要。判定時刻は snapshot.date の 12:00 UTC とみなす（数時間の誤差は4日幅の判定に影響しない）
// これによりタイムゾーンをエンジン入力に含めずに済む（原則F）
fun moonAge(date: LocalDate): Double {
    val jd = date.toEpochDay() + 2440588.0                    // その日 12:00 UTC のユリウス日
    val p = 29.530588853                                      // 朔望月
    return ((jd - 2451550.26) % p + p) % p                    // 基準新月 2000-01-06 18:14 UTC
}
// 月夜好きの条件: 13.0 <= moonAge(date) < 17.0
```

テストの期待値は本式で生成する。暦との照合は数件のみ・許容誤差 ±1日（§8）。

#### 計算関数（エンジンとUIで共有）

```kotlin
// :core:roll（純Kotlin）。MinimalBattleResolver・⑤の魔力集計・UI（修正値プレビュー／今日の相性）が同じ関数を呼ぶ
data class ArrowSource(val label: String, val quell: Int, val mana: Int)   // 例: ("雨好き・雨", +2, 0)
data class Arrows(val quell: Int, val mana: Int, val sources: List<ArrowSource>)

fun arrowsFor(slot: Int, party: Party, snapshot: ContextSnapshot): Arrows
```

- **UI側で同じ判定を再実装しない**。プレビューと実結果のずれを構造的に防ぐ（§8の一致テストで機械的に保証）
- `sources` は内訳（どの条件で何本か）。住人詳細の「今日の相性」の説明に使う
- 魔力の矢印は⑤で次のように効く：

```
manaGained = floor( (manaBase + manaPerQuell × q) × (1 + MANA_ARROW_RATE × Σ_i manaArrows_i) )
MANA_ARROW_RATE = 0.10（叩き台：ためこみ屋1体で +10%、欲張り1体で +30%）
```

### 5.4 ★分布の鎮め補正（テーブル駆動の線形補間）

```
w = base × (1−t) + boosted × t,   t = min(1, q / QUELL_NORM)
```

★1〜3 の帯を選んだ場合は、帯の中を★1:★2:★3 = **50:30:20** で分ける。この内訳は鎮め数による補正の対象にせず、base と boosted の両方に同じ比率を使う。

| テーブル | ★1 | ★2 | ★3 | ★4 | ★5 |
|---|---:|---:|---:|---:|---:|
| base | 42.5% | 25.5% | 17.0% | 12% | 3% |
| boosted | 35% | 21% | 14% | 20% | 10% |

モンテカルロ実測（QUELL_NORM=5）：鎮め0体→★5率3.0%、2体→7.4%、5体→12.6%。**単調・滑らか・定数2組だけで調整可能**であることを確認済み。空編成や `NoBattleResolver` では常に t=0 で素の分布に自然に退化する。

## 6. 定数テーブル

全確率・全閾値を単一の `RollConstants` に集約し、**PoC本番値とデモ値を別インスタンス**として持つ（コアループ仕様書§5確定事項）。

```kotlin
data class RollConstants(
    val starBase: Weights3, val starBoosted: Weights3,
    val star1To3: Weights3,                 // ★1〜3 の帯内比率（50:30:20）
    val quellNorm: Int,
    val personalityCount: Int,            // 12（v0.4確定。定義は Personality enum、§5.3）
    val rareColorRate: Double,            // 0.08
    val glowColorRate: Double,            // 0.01
    val awakenUpsideTable: List<Double>,  // 戦果→追加1体の確率（qは5で上限）
    val encounterRatePerHour: Double,     // 3.0（叩き台）
    val manaPerQuell: Int, val manaBase: Int, // POC / DEMO: 10 / 20
    // v0.4追加：勝率式と矢印（§5.2・§5.3）
    val memberBase: Double,               // 0.12
    val starPt: Double,                   // 0.02
    val arrowPt: Double,                  // 0.05
    val pMax: Double,                     // 0.90
    val manaArrowRate: Double,            // 0.10
    // v0.5追加：探索時間。Ignite の endAt = now + expeditionMinutes と ①遭遇生成が同じ値を読む
    val expeditionMinutes: Int,           // POC: 120 ／ DEMO: 3
) {
    companion object { val POC: RollConstants = ...; val DEMO: RollConstants = ... }
}
```

POC・DEMO ともに `manaBase = 20`、`manaPerQuell = 10` とする。魔力天井は `CEILING_COST = 400`。住人を魔力に還すときの基準値は★1で10、★が1段上がるごとに2倍とし、色倍率は通常×1・レア×3・発光×10とする（設計書03 §4.4）。

覚醒は毎周1体を確定し、鎮め数 `q` に応じて**最大1体を追加**する。POC の追加確率は `q=0〜2: 0%`、`q=3: 25%`、`q=4: 40%`、`q≥5: 50%`。DEMO は `q=0: 0%`、`q≥1: 50%` とする。

性格・材質・天気・曜日祭壇の**対応表そのもの**は定数ではなくルールなので `RollConstants` に入れず、`:core:model` の enum に持つ（設計書03 §2の「モチーフ・性格・定数テーブルはコード定義」に従う）。矢印1本の重み（`arrowPt`・`manaArrowRate`）だけを定数として調整する。

デモ値は「短時間で★5・発光色・上振れが見える」側に倒す（例：★5 20%、発光10%、探索3分）。探索3分では遭遇の期待値が小さくなるため、`DEMO.encounterRatePerHour` は「3分で平均6遭遇」になる値（120.0）にする。

**切替はビルドフレーバで固定する（v0.5確定・ADR D-003）。** `:app` に `standard`（本番相当、`RollConstants.POC`）と `demo`（`RollConstants.DEMO`、`applicationIdSuffix ".demo"`、表示名「精霊 DEMO」）の2フレーバを置き、プロセス内に定数は1組しか存在しない。実行時切替は採らない。実行時切替だと「このセッションはどちらの定数で計算したか」をセッション行に持つ必要が生じ（回収時に別の定数で再計算すると決定論が壊れる）、状態機械とスキーマに手が入るため。アラーム戦略（設計書04 §4.2）もフレーバに従う。

## 7. 数値検証：PoC初期定数での厳選期待値

PoC定数（★4+ 15%／★5 3%／レア色+ 9%／性格等確率）で、狙い個体が出るまでの期待覚醒数を解析・モンテカルロ（20万周）両面で確認した。

| 性格種数 | ★4+のみ | ★4+＆性格一致 | 3軸同時（★4+/性格/レア色+） | 完全体（★5/性格/発光） |
|---|---|---|---|---|
| 10種 | 6.7体 | 67体 | 741体 | 33,333体 |
| 12種 | 6.7体 | 80体 | 889体 | 40,000体 |
| 15種 | 6.7体 | 100体 | 1,111体 | 50,000体 |

覚醒ペースを1日3〜4.5体（2〜3周×上振れ込み）とすると、**3軸同時は素引きで約200〜300日**。これは実質「天井（魔力→指名覚醒等）前提の長期目標」であり、素引き圏の目標は「★4+（数日）」「★4+＆性格（数週間）」が担う。

この結果から導かれる設計含意：

- 短期（★4+）・中期（2軸）・超長期（3軸）の目標階層が**この定数のままで自然に成立している**。PoC初期値として妥当。
- ただし超長期目標が機能するには**魔力天井の出口が「指名覚醒」または「軸の部分保証」であることがほぼ必須**（天井なしの3軸は放置ゲーの時間感覚でも遠すぎる）。未確定事項「天井の出口」の判断材料として提示する。
- 性格種数10↔15の差は3軸期待値で1.5倍。攻略軸の豊かさと厳選の重さのトレードオフはこの範囲なら微調整レベル。→ **v0.4で12種に確定**（3軸同時 889体・素の分布基準）。

**v0.4追記（MinimalBattleResolver採用の影響）**：上表は鎮め補正なし（素の分布）の値である。バトルを入れると実効の★分布は base と boosted の間に来る。典型的な編成（3体・★2〜3）では ★4+ が約23〜25%になり、上表の期待覚醒数は**約0.6〜0.7倍に縮む**（§5.2の表）。重すぎる・軽すぎるの判断はデモでの体感を見てから、`QUELL_NORM` と `boosted` で調整する。

分布の実装検証：20万周のモンテカルロで覚醒0体の周は0（毎周確定の成立）、★分布実測 84.8/12.1/3.1%、色分布実測 91.0/8.0/1.0%と期待値に収束。
