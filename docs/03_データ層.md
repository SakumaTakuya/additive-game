## 1. 目的とスコープ

回収結果（設計書02の `ExpeditionResult`）の永続化先である住人コレクションと魔力経済、および厳選ループの出口（指名覚醒・重複を魔力に還す操作）のデータ設計を確定する。定義するのは：

1. ストア構成の確定（**Roomへの一本化**、設計書01への波及あり）
2. テーブル設計とトランザクション境界（特に**Collectの exactly-once**）
3. 厳選ループの操作：指名覚醒・重複を魔力に還す・保護フラグ・ニックネーム
4. 三層サーフェスが購読するクエリの定義
5. 天気の地域設定と保存値（v0.3）：取得元・取得タイミング・有効期限

## 2. ストア構成：Roomへ一本化する（設計書01への波及）

設計書01はセッションをDataStoreに置いたが、本書で**Roomの単一DBに一本化**する。

**理由：Collectの原子性。** 回収は「ロール結果の住人挿入＋魔力加算＋`collected=true`」の3書込であり、セッションだけDataStoreに分離すると2ストアをまたぐ部分失敗（Roomコミット後・DataStore書込前のクラッシュ）で不整合が生じ、冪等キーによる復旧ロジックが余分に必要になる。単一Roomなら**1トランザクションで全書込が原子的**になり、設計書01の不変条件I2（二重回収なし）がDBの機構でそのまま担保される。

原則A（不変の事実のみ保存）・原則B（フェーズは導出）は保存先に依存しないため、状態機械・TLA+検証結果は無傷。GlanceからのRoom購読も標準的な構成で問題ない。

> **設計書01改訂事項**：§3の「Proto DataStore」→「Roomの単一行テーブル」。`ContextSnapshot`（設計書02原則E）もセッション行に含める。**→ 01 v0.3で反映済み**

### 2.1 天気の地域設定と保存値（v0.3）

PoC方針の「ユーザーが手動で選んだ固定地域の天気をAPIで取得する（位置情報権限なし）」の実装定義。**設定画面は作らず**、地域の選択は編成画面ヘッダから開くダイアログで行う（設計書05 §6.6）。

**保存先：Roomの単一行 `app_settings`**（§3）。一本化方針を維持し、ストアを増やさない。Collectの原子性とは無関係な値だが、DataStoreを足すとストアが2つになり、AIエージェントの実装・テスト対象が増えるため。

**取得元：気象庁の予報JSON（PoC実装）**

```kotlin
interface WeatherSource {                       // :core:data。差し替え点
    suspend fun fetchToday(regionCode: String): WeatherKind   // 失敗時は例外
}
// PoC実装 : JmaForecastSource  — https://www.jma.go.jp/bosai/forecast/data/forecast/{regionCode}.json
// 代替実装: OpenMeteoSource    — 座標で取得。無料版は非商用限定のため、顧客デモで使う場合は利用条件を確認
```

- 「今の天気」（観測）ではなく**「今日の天気」（予報）**を使う。編成画面は「今日：☔雨」と見せて今日の編成を考えさせる作りであり、1時間ごとに変わる現在値では編成画面で見た天気と点火時の値がずれうるため
- 値の取り出し：レスポンス先頭要素の `timeSeries[0].areas[0].weatherCodes[0]`（県内の代表区域・直近の予報）。**天気コードの先頭桁で4区分に写す**（1→SUNNY、2→CLOUDY、3→RAIN、4→SNOW、それ以外→取得失敗扱い）。写像は採用前に実データで確認する
- このJSONは公式に文書化されたAPIではなく、形式が予告なく変わりうる。対策として、保存した実JSONを入力にしたパーサテスト（数都道府県分）を `gradlew test` に常設し、壊れたときは取得失敗として後述の中立に落とす
- 出典表記「出典：気象庁ホームページ」を地域選択ダイアログに常時表示する。採用前に気象庁ホームページの利用規約を一度確認する
- 必要な権限は `INTERNET` のみ（インストール時に付与される通常権限。権限不要方針の範囲内）

**地域リスト**：47都道府県を `:core:model` にコード定義し、各都道府県に予報区コードを1つ対応させる（`area.json` の `offices` から選ぶ）。北海道・沖縄など予報区が複数ある県は県庁所在地を含む区域を代表とする（例：北海道＝石狩・空知・後志地方、沖縄＝沖縄本島地方）。

**取得タイミング**（天気のための常駐ジョブは作らない）：

| 契機 | 条件 |
|---|---|
| アプリが前面に来たとき | 保存値が1時間以上古い場合のみ |
| 編成画面を開いたとき | 同上 |
| 地域を変更したとき | 即時 |

取得に失敗したときは保存値を**上書きしない**（有効期限内の前回値がそのまま使われ続ける）。

**有効な天気の導出（単一の関数を全員が使う）**：

```kotlin
// :core:data。Ignite（01 §5）・編成画面のプレビュー・IDLE中のWidgetの空がすべてこれを呼ぶ
fun effectiveWeather(s: AppSettingsRow, now: Instant): WeatherKind = when {
    s.regionCode == null || s.weatherFetchedAt == null   -> WeatherKind.UNKNOWN   // 未設定・未取得
    now - s.weatherFetchedAt > WEATHER_MAX_AGE          -> WeatherKind.UNKNOWN   // 古すぎる → 中立
    else                                                 -> s.weatherKind
}
val WEATHER_MAX_AGE: Duration = 6.hours   // 叩き台（kotlin.time）
```

- `UNKNOWN`（中立）の日は、天気に関わる性格・材質の修正値がすべて不発になる（設計書02 §5.3）。誰かだけが得をしないので公平
- プレビューと点火が同じ関数を通るため、編成画面で見た天気がそのままスナップショットに固定される（設計書02 §5.3 原則2）
- Igniteはこの関数を呼ぶだけでネットワークに触れない（01 §5）

## 3. テーブル設計

モチーフ（初期住人10体）・性格・定数テーブルは**DBに入れずコード定義**（`:core:model` の enum/リスト）。DBに入れるのは動的な状態のみ。

```
session            -- 単一行（最新セッションのみ。PoCでは履歴なし）
  id INTEGER PK, startedAt, endAt, seed, snapshotDate, snapshotTimeBand, snapshotWeather,   -- v0.3: snapshotTimeBand 追加
  partyJson,       -- 個体IDの順序付きリスト。[0]が隊長
  collected BOOLEAN

resident           -- 覚醒済み住人の個体
  id INTEGER PK AUTOINCREMENT,
  motifId INT, star INT, personalityId INT, colorTier INT,
  acquiredAt, sourceSessionId INT,   -- 出自（指名覚醒は負値等の別ソース識別、要確定）
  locked BOOLEAN DEFAULT 0,          -- 保護フラグ。「魔力に還す」対象から除外
  nickname TEXT NULL                 -- v0.2: ユーザーが付ける名前。ロール対象外（コアループ v2.1 §5）

mana               -- 単一行の残高
  id INTEGER PK CHECK(id=1), balance INT, lifetimeEarned INT

collection_receipt -- 回収の冪等レシート
  sessionId INTEGER PK               -- 二重回収をDB制約でも防ぐ（二重防御の実体）

app_settings       -- v0.3: 単一行の設定と天気の保存値（§2.1）
  id INTEGER PK CHECK(id=1),
  regionCode TEXT NULL,              -- 気象庁の予報区コード。NULL＝未設定
  weatherKind INT NULL,              -- 最後に取得できた「今日の天気」（WeatherKind）
  weatherFetchedAt INTEGER NULL      -- 取得時刻（壁時計）。有効期限の判定に使う
```

補足：

- `partyJson` は正規化テーブルにせずJSON1列とする。編成は「丸ごと差し替える小さな順序付きリスト」であり、結合クエリの必要がない。個体削除（魔力に還す）時の整合はRepository層で除去する。
- `lifetimeEarned` は天井演出（累計で溜まっていくゲージ）用。残高と分離しておくと消費後もゲージ表現の自由度が残る。
- 図鑑（モチーフ発見済みか）は `resident` からの導出（`SELECT DISTINCT motifId`）で足り、テーブルを持たない。指名覚醒の選択肢＝発見済みモチーフもこのクエリで出る。

## 4. トランザクション境界

### 4.1 Collect（回収）— exactly-once の実体

```kotlin
@Transaction
suspend fun collect(session: SessionRow, result: ExpeditionResult) {
    // ガード（原則D）: 呼び出し前に derive()==RETURNED 検証済み。ここではDB防御のみ
    insertReceipt(session.id)                 // PK衝突＝二重回収→例外でロールバック
    insertResidents(result.awakened.map { it.toRow(session.id) })
    addMana(result.manaGained)
    markCollected(session.id)
}
```

設計書01 §5の「単一トランザクション＋冪等性キー」がこの4行に対応する。TLA+で検証した `CollectConsistent` のDB側の実装がレシートPKである。

### 4.2 Ignite（点火）

`derive()==IDLE` ガード後、セッション行を新規値で置換（単一行UPSERT）。`partyJson` は前回値を引き継いだ編成画面の確定値。

### 4.3 指名覚醒（天井消費）

```kotlin
@Transaction
suspend fun namedAwaken(motifId: Int, seed: Long) {
    require(balance >= CEILING_COST)
    val roll = rollEngine.resolveNamed(seed, motifId, constants)  // 設計書02 v0.2 §4
    insertResident(roll.toRow(sourceSessionId = NAMED_SOURCE))
    addMana(-CEILING_COST)
}
```

- モチーフは指名で確定、**★・性格・色は通常ロール**（3軸の当たり外れは残す。指名の価値は「狙いモチーフの試行を魔力で買える」こと）
- シードは実行時に採番して即時解決（セッションと無関係の単発処理。決定論はテスト用にシード注入可能な形で保つ）

> **設計書02改訂事項**：`resolveNamed(seed, motifId, constants): ResidentRoll` をエンジンAPIに追加。ストリームラベルは `"named.star"` 等で通常覚醒と分離。**→ 02 v0.2で反映済み**

### 4.4 重複を「魔力に還す」（旧称：変換）

世界観上の呼称を「魔力に還す」とする（愛着を損なわないための言い換え。データ・処理は不変）。

- **手動操作のみ**（複数選択→一括）。自動化は誤爆リスク（当たり個体の溶解）が厳選ゲーの信頼を直撃するためPoCでは実装しない
- `locked = true` の個体と**編成中の個体**は対象外（Repository層でフィルタ＋UI側でも非活性）
- 還元魔力は `10 × 2^(star−1) × colorMultiplier`。通常色は×1、レア色は×3、発光色は×10（★1の基準は10）

### 4.5 ニックネーム（v0.2）

`UPDATE resident SET nickname = ? WHERE id = ?`。単一列更新、トランザクション不要。前後空白を除き、空文字はNULLに正規化する。最大10文字とし、改行・制御文字を禁止する。表示は「nickname ?: モチーフ名」。保護フラグのUI呼称は「保護」とする（DEC-10）。

### 4.6 初期付与（v0.2・初回起動時のみ）

```kotlin
@Transaction
suspend fun seedInitialResidentIfEmpty(seed: Long) {
    if (countResidents() > 0 || session() != null) return   // 冪等
    val roll = rollEngine.resolveNamed(seed, motifId = 1, constants)  // ★・性格・色は通常ロール
    insertResident(roll.toRow(sourceSessionId = INITIAL_GIFT_SOURCE))
}
```

- モチーフは#1（スライムの精霊）固定。★・性格・色は通常の個体ロール分布を使い、★3以上を保証しない（DEC-11）。特別扱いはこの付与のみで、以降#1は他と同列
- `resolveNamed` を流用（設計書02 §4）。ストリームラベルは `"named.*"` を共用してよい（1回限りの処理で相互干渉なし）
- 出自は `INITIAL_GIFT_SOURCE = -2L`（指名覚醒 -1 と区別）

## 5. Repository構成と購読クエリ

```
SessionRepository    sessionFlow: Flow<SessionRow?>        … 三層サーフェスの導出元（設計書01）
ResidentRepository   residentsFlow / caretakersFlow(partyIds除外=留守番組)
                     partyFlow(partyJson展開・[0]=隊長) / discoveredMotifsFlow(図鑑・指名候補)
ManaRepository       manaFlow(balance, lifetimeEarned)      … 天井ゲージ表示
WeatherRepository    settingsFlow(地域・天気・取得時刻) / refreshIfStale() / setRegion(code)
                     … 編成画面ヘッダ・IDLE中のWidgetの空・Igniteのスナップショット（§2.1）
CollectUseCase       :core:domain。derive()ガード→エンジン呼出→collect()の編成
```

Widget（Glance）は `sessionFlow` ＋ `caretakersFlow` の2本だけで描画できる（設計書01 §6.2の留守番組ルールに対応）。チップ・通知は `sessionFlow` のみ。

## 6. PoCスコープの割り切り

- セッション履歴なし（単一行置換）。統計・実績は製品版
- スキーマは version 3（v0.3：`app_settings` 追加、`session.snapshotTimeBand` 追加）
- マイグレーション戦略は `fallbackToDestructiveMigration` を許容（PoCデータは使い捨て）。ただしスキーマexportはONにしてAIエージェントの差分検証対象に含める
- バックアップ/クラウド同期なし（完全ローカル方針どおり）
- 天井値・還元レートは §7 に定義する（定数はコード側）
